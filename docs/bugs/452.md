# PR detail makes two serial round trips: branch protection waits for getPR (#452)

- **Area:** prs
- **Symptom:** Enter on a PR showed the skeleton for a full round trip, then the protection-dependent sections filled in one round trip later (measured 52 -> 1057 ms for `pr view`, 1113 -> 2117 ms for protection with a 1000 ms fake delay).
- **Root cause:** `src/features/prs/detail.jsx` derived the `getBranchProtection` branch from `pr.baseRefName`, so the request could not start until `getPR` returned.
- **Fix:** `PRDetail` takes the list row's `baseRefName` (passed by `app-views.jsx` from the selected item) and starts `getBranchProtection` in the same render as `getPR`. When `getPR` returns a different base the key changes and protection refetches for the real base. When the base is unknown (no row) it still waits for `getPR`.
- **Regression test:** `src/features/prs/detail-parallel.test.jsx` > `asks for branch protection with the list-row base branch before getPR returns` (failed before the fix).
- **Sibling sweep:** Issue detail has no dependent second request. `getPRChecks` still does its own `pr view` for the head SHA before the check-runs call (needs `headRefOid`, which the list query does not return); left for the list/checks query lane.
