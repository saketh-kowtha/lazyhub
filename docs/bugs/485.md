# A dead, duplicate or lying key could reach main (#485, R7 part)

- **Area:** app | keys
- **Symptom:** the same class of bug kept shipping (#445, #446, #447, #449, #511): a hint, help row or chord named a key that did nothing in that pane.
- **Root cause:** nothing checked rendered hints against the registry; the checks-mode, sidebar, leader and picker hints were hand-written strings, and footer/help rows carried no action id to check.
- **Fix:** footer hints and help rows now carry the registry `id`. `src/config/key-ownership.test.js` is generated from the registry and runs in `npm test`: every footer/help/which-key entry in every (pane, view) names an action that is bound and live there; the global help block lists only app-level actions that are bound; every declared chord (`g l`, `gg`, `g p`) resolves through `resolveChord()`, the function the view resolver uses; every bound action of a scope appears in the source that owns it. Hand-written hint lines in PR detail, checks mode, pickers, the leader hint and the sidebar footer are replaced by `hintLine()`.
- **Regression test:** `src/config/key-ownership.test.js` (all tests; the chord and handler tables fail on a registry key with no resolver or handler).
- **Left for later (Part of #485):** replacing `test/input-bus.js` with the real focus manager in the e2e suites, the real-stdin PTY keypath tests, and moving the remaining literal-key views (ConflictView, NewPRDialog, Settings, Logs, CustomPane, AIReviewPane, AIAssistant, Onboarding) onto the registry (R9, #487).
- **Sibling sweep:** all ten (pane, view) contexts are in the table.

## R7 slice 2: guards under dialogs, popover hint, PTY keypath


- **Area:** app | prs | settings
- **Symptom:** the PR preview popover said `a approve  m merge` even after the user rebound or unbound those keys. Panes kept their own `if (dialog) return` guard because a scope-less listener received every key regardless of the focus stack.
- **Root cause:** the popover hint was a string literal next to the handler; the router had no way to say "this listener stays silent while an overlay, dialog or input owns the keys", so each pane re-implemented it.
- **Fix:** `yieldToModal` on focus entries (`src/focus/router.js`, `useFocusEntry`, `useKeymapInput`, `useInput`); the scope ladder moved to `src/focus/scopes.js` (re-exported by `keyscope.js`). Settings and CustomPane drop their guard. `previewHint()` derives the popover bar from the effective bindings. New tests: scope-ownership checks in `key-ownership.test.js`, a ratchet over hand-typed `[key] label` literals (`hint-literals.test.js`), a one-root-listener check, and a PTY key-ownership flow.
- **Regression test:** `src/settings-pane.e2e.test.jsx` > "keys typed into the Page Size editor never reach the pane handler" (failed with the guard removed and no `yieldToModal`); `src/focus/router.test.js` > "yieldToModal"; `src/features/prs/list-row.test.jsx` > "preview popover hint bar".
- **Sibling sweep:** guards in PR list, issues list, branches, actions and notifications run work first (dismiss a persistent status) or sit beside inline dialogs; PR detail, diff and issue detail handle compose, confirm and search in the same handler (input scope). They stay until each is migrated, so as not to change behaviour.
