# TUI disk and memory cache keys did not include host or account (#520)

- **Symptom:** the same `owner/repo` cached while using github.com was served as stale data to a GHES host (or to another `gh` account) on the next launch, because the disk cache key was `hash([repo, fn, deps])` and the in-memory key `[fn, ...deps]`. `lazyhub status` also read the newest cached lists regardless of host.
- **Root cause:** `useGh` built both keys from the repo and arguments only. The daemon cache already scoped by host and account; the TUI cache never did.
- **Fix:** `src/cache.js` gains `scopedCacheKey()` (host from `GH_HOST`, lowercased, plus an account fingerprint). The fingerprint is a one-way digest of the credential `checkAuth()` already fetches, so there is no extra lookup on any read, and the credential itself is never stored or logged. `useGh` uses the scoped key for disk and includes host and account in the memory key; entries record `meta.host`, and `lazyhub status` only reads entries for the current host. Old unscoped entries are simply never matched.
- **Residual:** `lazyhub status` has no authentication step, so it is scoped by host only. A misses-only change: switching accounts or rotating a token starts from a cold cache.
- **Regression tests:** `src/hooks/useGh.test.jsx` (host, account, mid-session host change, same identity still hits), `src/cache.test.js`, `src/bootstrap.test.js`, `src/cli/status.test.js`.
