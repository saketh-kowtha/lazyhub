# A failed author filter kept its error in the footer after leaving the PR pane (#564)

- **Symptom:** in the PR list, `@`, a login that does not exist, Enter: the error shows (correct). Switching to Issues or Actions left the same error in the global footer.
- **Root cause:** `useGh` reported every failure to `useGhHealth` per call site and the only way to clear it was a later success of that same call site. Leaving the pane never retried the query, so the call site stayed failing. Also, a 422 or unknown-user error is caused by the user's own input, not by a degraded gh connection, yet it went to global health.
- **Fix:** `recordGhFailure` classifies the error with `classifyGhFailure`; only connection, login, scope and rate-limit classes enter global health. Input-caused failures stay in the owning pane (which already renders its `error` with `FailureNotice`). `useGh` now clears its call site's failure when the owner unmounts or its key changes (`clearGhFailure`). A real network failure still shows globally until a success, a key change or unmount.
- **Regression test:** `src/hooks/useGh.test.jsx` "useGh scoped failures (#564)": bad author never reaches global health; a connection failure clears on unmount and on key change and otherwise stays global.
