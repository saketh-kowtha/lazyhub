# Merge and review flows: raw CLI flags, 5 keystrokes to merge, Enter does not approve, inconsistent chrome (#468)

- **Area:** prs
- **Symptom:** The merge picker listed `--merge / --squash / --rebase` and the confirm read "Merge PR #142 via --merge?". A merge took `m`, Enter, Enter, Left, Enter. Enter on the approve box did nothing (Ctrl+G only). The commit-message step had no input box and no PR title. Dialogs used different borders, padding and hard-coded colours.
- **Root cause:** `MERGE_OPTIONS` (`list-row.jsx`, `detail.jsx`) used the CLI flag as the label; `OptionPicker` always opened a message step after Enter; `ConfirmDialog` defaults to No; `FormCompose` text fields only advanced to the next field on Enter; `ConfirmDialog` hard-coded `#f85149` / `#3fb950`.
- **Fix:** Human labels ("Create a merge commit", "Squash and merge", "Rebase and merge", "... (bypass branch protection)") live in `src/features/prs/merge-methods.js` (re-exported from `list-row.jsx`). In PR detail `m` opens a picker only after repo settings have loaded; it lists the methods the repository allows (admin bypass only for admins), puts mergeability, CI and approvals in the title, and preselects squash when allowed. Choosing a method never merges by itself: a confirm "Merge PR #N via <method>?" (default No) follows, and an admin bypass additionally needs the PR number typed. `e` adds a commit message first. The diff view merge uses the same picker and confirm (`merge-methods.js`; `confirmMerge` keeps the `runWrite` wrapper). Approve (detail, diff, list) goes through `ReviewDialog`: Enter on the comment form opens "Approve PR #N?" (default No); request changes needs a reason. `FormCompose` submits on Enter from the last text field, shows a validation message, and Enter in a multiline field stays inert. `OptionPicker` gains `promptKey` and `initialIndex` and a titled, bordered message step; `ConfirmDialog` uses theme tokens and the same chrome.
- **Regression test:** `src/features/prs/detail-merge.test.jsx`, `src/components/dialogs/OptionPicker.test.jsx` > `OptionPicker promptKey and initialIndex`, `src/components/dialogs/FormCompose.test.jsx`.
- **Sibling sweep:** The list pane merge flow (`list-dialog-view.jsx`) got the labels only (it already confirms with a default-No dialog). The New Issue form now requires a title.
- **Rest (batch C):**
  - The footer for the list-view dialogs was chosen by dialog name, and the names `merge-confirm`, `auto-merge`, `close` (issues), `delete` (branches), `rerun`/`cancel` (actions) and `new` (issues) were not in `DIALOG_HINT_MAP` (`src/app-views.jsx`), so the list hints stayed under an open confirm. They now map to the confirm or compose hints. The `[DIALOG]` badge itself was already present because `ConfirmDialog` claims the dialog scope; the missing part was the footer.
  - One box style: the command palette used a double border (`╔`); it is now round like every other dialog. The issue detail header was a full single-line box; it is now the same bottom rule as the PR detail header (`PRDetailHeader`), both with `t.ui.border`.
  - One hint bar in detail views: the footer is the only place for key hints. The issue detail's own `[c] reply [l] labels ...` bar is gone, the scroll line no longer repeats `[j/k] scroll [gg/G]`, and the PR detail's in-view row now shows only a status message, the scroll position or the conflict notice. Check-mode keys still show in the Checks section header.
  - Titles: the PR and issue label, assignee and reviewer pickers show `Labels: PR #N`, `Assignees: issue #N` and so on, in the loading and error states too.
  - The screen snapshot for the palette was updated for the border change (linked to this bug).
- **Left:** nothing from the issue.
