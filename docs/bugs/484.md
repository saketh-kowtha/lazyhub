# Dialogs owned keys by flag, not by position on the stack (#484, R6 part)

- **Area:** app | keys
- **Symptom:** a component that opened a dialog had to remember `notifyDialog(true/false)`; `App` kept the answer in `dialogActiveRef` and compared a render-time `activeScope` string, so a missed call or a stale string let a global key (pane jump, palette, help) fire under a dialog.
- **Root cause:** two sources of truth for "a dialog is open": the focus stack (`useKeyScope`) and a ref set from a passive effect in every pane.
- **Fix:** every `notifyDialog` caller (PR list/detail/diff/conflict, issues list/detail, branches, actions, notifications, logs, settings, custom pane, AI assistant) now claims `useKeyScope('dialog', open)` on the focus stack (or already claimed `overlay`, so the call was dropped). `App`'s global key handler moved from a root `useInput` to `useFocusGlobals` (runs after the entries, once per key) and reads the live router scope (`liveScope()`, `isModalScope`, `isViewScope` in `src/keyscope.js`). `notifyDialog`, `dialogActiveRef` and the `activeScope` string compare are deleted; the debug-state `dialog` field comes from the stack.
- **Regression tests:** `src/focus/FocusProvider.test.jsx` (globals run once, after entries, and see the dialog on top), `src/app.e2e.test.jsx` (digits dead under a pane dialog), `issues.test.jsx` and `diff/state.test.jsx` (the stack top is `dialog` while open, released after).
- **Gotcha:** the Ink test doubles ignore `isActive`, so the no-provider fallback of `useFocusGlobals` re-checks the provider in its handler; without that the global handler ran twice per key under the screen matrix.
- **Left for later (Part of #484):** peers at the active scope still all receive a key (R5 note); the status bar scope indicator and the `showHelp` branches in `app.jsx` still read scope strings; the prefix and leader timers stay in `app.jsx` (R9).
