# Diff and log views blank on revalidate and refetch what cannot change (#597, lane V4b)

- **Area:** prs (diff), actions (run logs), executor (additive fields)
- **Symptom:** opening the diff showed a skeleton from the first frame and again whenever the file list revalidated; reopening the diff of an unchanged PR re-listed the files and re-fetched every patch; the Actions log dialog replaced itself with a spinner and re-downloaded the whole run log on every open.
- **Root cause:**
  - The diff body and the log dialog branched on a hand-coded `loading` flag, and their reads were keyed by PR number / run id alone, so they could only be given the 30 s window, although a file list and a patch are fixed for a head commit and a completed run attempt's log is fixed for good.
  - Patches lived in a hook-local ref, lost on every remount.
- **Fix:**
  - `src/features/prs/diff/keys.js`: file list, later list pages and each patch are read under keys that carry the head SHA and use the `immutable` freshness class (`src/data/freshness.js`). The SHA comes from the PR detail query (shared with the detail view, 5 min window while the diff is open) and, on a cold open, from the file-list response itself (`headRefOid`); a cold read lands under the `''` key (30 s) and seeds the key of the head it returned, so there is no second call. GitHub cannot read "files at SHA x", so each response is checked against the key (`headRefOid` on the list, the commit in a file's `blob_url`); a response from a newer head is never stored under the older key, the detail query is invalidated so the SHA moves on, and `HeadMovedError` keeps the rows meanwhile.
  - `usePRDiffFiles` returns the derived `mode`; `DiffView` branches on it (skeleton only after 150 ms, nothing new before, rows stay while a newer head loads). `r` drops the SHA-keyed values of the visit and reads again.
  - `prefetch.js` (R4) warms the same key (SHA when known, else the plain one) with the same signature.
  - `src/features/actions/run-log.js` + `RunLogDialog.jsx`: the run log and the failure excerpt are `useGh` reads keyed by run id + `updatedAt` + `attempt`; immutable for a completed run, `ttl: 0` (earlier text kept while it re-reads) for one still going. Transient excerpt outcomes (pending, rate limit, unavailable) throw so they are never cached as final. `gh run list` is not asked for `attempt` (older gh versions reject unknown JSON fields), so `updatedAt` (it moves on a re-run) stands in; `--attempt` is passed when `attempt` is present and above 1.
  - Executor, additive only: `listPRFilesPage` returns `headRefOid`; `getPRFilePatch` returns `headSha`; `getRunLogs(repo, id, attempt)` and `getFailedLog({ runId, attempt })` accept an attempt.
- **Not done here:** `detail.jsx` still calls `getFailedLog` directly for a check's job log (V4a owns it). A job id is already unique per attempt, so it can adopt `useGh(..., { freshness: 'immutable' })` the same way; the transient-state rule above applies. When the SHA changes the patches of the old head are dropped (the diff is different content), so file notes read "Loading this file" for a moment.
- **Regression tests:** `src/features/prs/diff/immutable.test.jsx`, `src/features/actions/run-log.test.jsx`, `src/features/prs/diff/no-loading-branch.test.js`, executor tests for `headRefOid`, `headSha` and `--attempt`.
