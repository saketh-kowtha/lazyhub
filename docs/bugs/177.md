# Review queue: explainable attention queue, first slice (#177)

- **Area:** app
- **Symptom:** (feature, not a bug) Focus listed review requests and your PRs as plain rows with no CI, no repository and no reason they needed attention.
- **Root cause:** n/a. This file records what shipped and what did not.
- **Fix:** `g q` opens the review queue (mockup variant B, `docs/mockups/review-queue-account-wide.md`): a status sidebar (chip line below 118 columns) and a list of the focused group, read-only. It reads the account-wide evidence from `fetchReviewQueueEvidence` (#175, one GraphQL round trip per page) and shows, per row, the attention reason that placed the PR in its group ("review requested of you", "via team @acme/core", "1 of 2 checks failing", "waiting for a review"...); a `why` strip under the list lists every reason with the inspected head, CI counts and the age of the read. Unavailable facts say so; a PR with unavailable key facts goes to "Unavailable data", never "Ready".
- **Seam for #127:** `Enter` calls `goToQueueItem` in `src/app.jsx`, which opens the existing PR detail with the evidence record attached as `_evidence`. The evidence view replaces that one callback. Back (`Esc`) returns to the queue with group and row kept (remembered by PR identity), and the loaded rows are reused while younger than 60 s.
- **D16 (printed in the view):** each page is 30 PRs per search; `not all loaded: review requests (N in all), your PRs (M in all) · + loads more`; `+` fetches the next page of every search that has one. A refresh that fails keeps the rows and says so.
- **Keys added:** `g q` (global), and in the queue `Enter` open, `o` browser, `]`/`[` group, `+` more (`j/k`, `gg/G`, `r` are the shared list keys).
- **Not done:** ranking inside a group beyond most-recent-first, signal badges, queue search (`/`), scope filters (org / saved sets) and per-host switching, collision (#360) and claims (#361) signals, making the queue the home screen instead of a view over Focus, and a `d` files-changed key. The authored search is fetched again as page one when only the review-requested search has a next page (the executor takes one cursor per search and has no "skip"); results are deduplicated and the finished search's totals are not overwritten.
- **Regression test:** `src/features/queue/model.test.js`, `src/features/queue/view.test.jsx`, `src/review-queue.e2e.test.jsx`.
- **Sibling sweep:** `queue.browser` added to the fuzzer's spawning actions (`src/random-keys.e2e.test.jsx`); `◔` added to the ASCII glyph map.
