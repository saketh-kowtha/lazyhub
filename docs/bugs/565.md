# Issue detail was one flat `gh issue view --json comments` call (#565)

- **Symptom:** opening an issue with hundreds of comments read every comment in one call, showed only comments (no label, assignment, close/reopen, rename or cross-reference events), and had no quote reply, edit, delete, reactions or live updates.
- **Root cause:** `IssueDetail` used `getIssue` (`gh issue view --json ...,comments`) and rendered the array flat; nothing cursor-paged and nothing revalidated.
- **Fix:** the detail view now reads the header with `getIssueHeader` (no comments) and the conversation with `listIssueTimelinePage` (`src/executor/issue-timeline.js`): GraphQL `timelineItems` with `after:` cursors, comments plus labelled/unlabelled, assigned/unassigned, closed (with reason and closing PR or commit), reopened, renamed, cross-referenced and connected/disconnected events, with reactions, `authorAssociation`, `isMinimized`/`minimizedReason`, `lastEditedAt`, `viewerCanUpdate`/`viewerCanDelete`. The controller mirrors the PR conversation view: later pages are appended and never refetched, the footer shows "N of M timeline items", the next page loads near the end. `Q` quote-replies (`>` lines and a link), `e` and `Ctrl+X` edit and delete only the viewer's own comments (`editIssueComment`/`deleteIssueComment` are REST writes the classifier recognises; delete defaults to No). While the view is the one on screen, page 1 and the header are revalidated every `[features.issues].refresh_seconds` (default 30, minimum 15), paused while a dialog, compose box, delete confirm or load is open; edits fold in by content signature and items past the loaded pages arrive as a "N new comments" marker outside the scrolling rows (`n` loads them). Every GitHub string is rendered through `sanitize()`; the skeleton shows in the first frame.
- **Regression tests:** `src/executor/issue-timeline.test.js`, `src/features/issues/timeline-state.test.js`, `src/features/issues/detail-timeline.test.jsx`, `src/config/schema.test.js`.
