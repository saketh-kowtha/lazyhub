# gh missing at runtime is classified as unknown and loses the spawn error (#441)

- **Area:** app
- **Symptom:** When the `gh` binary is not on PATH, the user saw a generic "gh pr list --repo failed" message and the failure was classified as `unknown` instead of `gh_missing`, so the actionable "install gh" guidance never appeared.
- **Root cause:** `execa` runs with `reject: false`, so a spawn failure resolves instead of throwing. The resolved result has `failed: true`, no `exitCode`, empty `stderr`, and the reason in `shortMessage`/`message`/`code`. The `result.exitCode !== 0` branch in `src/executor/core.js` ignored all of that, building a message with no code, and `GhError` carried no `code`, so `classifyGhFailure` never saw `ENOENT`.
- **Fix:** `GhError` accepts an optional `code`. In the `result.exitCode !== 0` branch of `runGh`, a result with no exit code and `failed: true` is treated as a spawn failure: the message comes from `shortMessage`/`message` (still redacted for 40+ char runs), `exitCode` is 127, and `code` is `result.code`. `stderr` and all other paths are unchanged.
- **Regression test:** `src/executor/core.test.js` › `runGh spawn failure` › a missing gh binary is classified as gh_missing, not unknown; a missing gh binary keeps the spawn error text and a numeric exit code (both failed before the fix).
- **Sibling sweep:** Other `runGh` callers go through the same branch, so they all receive the spawn error. Read paths that bypass `runGh` are out of scope; none were found.
