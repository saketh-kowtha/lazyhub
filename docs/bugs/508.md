# PR list paging refetched from page 1, carried heavy rows and stopped silently at 1,000 (#508)

- **Symptom:** nearing the end of the list raised `limit`, which changed the cache key, so `listPRs` re-paged from page 1 (55 GraphQL calls to reach row 1,000). Each row requested 50 check contexts plus body. At GitHub's 1,000 search cap the list just stopped.
- **Root cause:** one limit-based query instead of cursor pages; row query used `statusCheckRollup.contexts(first: 50)` and `body`.
- **Fix:** `listPRsPage` fetches one cursor page (`after: endCursor`) and the list appends it, never refetching earlier pages; only a filter/scope/author/sort change or `r` restarts, and a failed page is retried alone. Rows are slim: CI is `checkSummary` counters, `body` and the full check list load for the focused row only (`getPRPreview`). Writes patch the row via `getPRRow` instead of resetting pages. The footer shows "N of M", "loading more", the retry hint, and a notice at the 1,000 cap. State sets are expressed server side (closed means closed and unmerged) so the total is exact; open+merged cannot be one search and shows "N loaded". Oldest-first sorts on the server.
- **Regression tests:** `src/executor/prs.page.test.js`, `src/features/prs/list-paging.test.jsx`, `src/features/prs/list-view.test.jsx` (paging footer).
- **Not done:** sending `/` to GitHub search (reaching older PRs past the cap) needs a design decision; the notice tells the user to refine the filter.
