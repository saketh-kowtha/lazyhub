# PR list could not reach past 1,000 results (#508, remainder)

- **Symptom:** the PR list loaded at most the newest 1,000 results of a state filter, and `/` only jumped between rows that were already loaded, so older PRs in a large repository were unreachable.
- **Root cause:** GitHub search returns at most 1,000 results per query and the list had no way to send a narrower query. Cursor paging and slim rows (the rest of this issue) landed earlier with the PR list paging work.
- **Fix:** `/` now opens "Search pull requests". The text goes to GitHub as a server-side query (`listPRsPage({ search })`) appended after the pinned `repo:` and `is:pr` qualifiers, paged by cursor like any other filter, with the same "N of M" counter and the cap notice ("refine the search"). A query that names its own state (`is:closed`, `-is:merged`) replaces the state filter. `validatePRSearch` refuses `repo:`, `org:`, `user:`, `owner:`, `type:`, `sort:`, `is:issue`, control characters and queries over 256 characters, with the reason shown in the dialog, so a search can never leave this repository. An empty query clears it. The old local fuzzy jump is gone from the PR list.
- **Regression tests:** `src/executor/prs.page.test.js`, `src/features/prs/list-paging.test.jsx`, `src/features/prs/list-dialog-view.test.jsx`.
