# Large-repo completeness budgets as a CI gate (#510, part)

- **Area:** ci | executor
- **Symptom:** a new `first: N`, `--limit` or `per_page` could silently cut a list off, and nothing in CI noticed. The existing gates (512 MB PTY journey, 1,200-PR scale journey, keystroke budgets, screen matrix) cover memory, latency counts and layout, not completeness.
- **Root cause:** completeness was a convention, not a check.
- **Fix:** `src/paging-audit.test.js` pins every fixed-size gh call per file with the reason it is complete (paged by cursor, nested preview with `totalCount`/`pageInfo`, or capped with a visible notice). A new site, or a removed one, fails `npm test` until it is listed with its reason.
- **Regression test:** `src/paging-audit.test.js`.
- **Second slice (PR "large-repo budgets as a CI gate"):** `test/support/gh-shim/perf.mjs` is a generated, seeded fake `gh` (5,000 open PRs, 80,000 closed, 2,000 issues, a 3,000-file / 100,000-line diff with a 40,000-line file and an omitted patch, 400 conversation comments, 150 threads with one 120-reply thread, GitHub's 1,000-result search cap) with a fixed per-call delay (`LAZYHUB_GH_DELAY_MS`). `test/perf/run.js` (`npm run test:perf`) drives the built TUI against it and asserts first-row time, paging completeness (cap notice, every cursor once, in order), per-file diff loading (no `pr diff`), the "too large" notice, conversation and thread-reply paging, and peak RSS. CI job `Performance budget`. Numbers: `docs/PERF_BUDGETS.md`. Proof the gate bites: with PR list paging stopped after the second page, the run fails ("timed out waiting for PR list cap notice", list stuck at 200 items).
- **Regression test:** also `npm run test:perf`.
- **Left (Part of #510):** the 250-check and 600-notification fixtures, search over the 80,000 closed PRs, the keypress-to-frame p95 and warm-navigation (0 gh calls) budgets, `getGhCallHistory()` exact counts per action, and `it.fails`-style pins for gaps that #480-#482 close.
